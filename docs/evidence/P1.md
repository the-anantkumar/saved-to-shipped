## What the measurements establish

The initial local workerd run used separate metadata/content tables, two secondary indexes, source uniqueness, 12 groups, 20 synthetic job records and a small operational reserve. Bodies and notes include several scripts and emoji; the varied profile uses item-specific vocabulary. Bytes below are decimal, not MiB.

| Fixture | Logical bytes | SQLite used bytes without FTS | SQLite used bytes with rebuilt FTS |
| --- | ---: | ---: | ---: |
| 500 typical saves | 1,168,501 | 1,589,248 | 1,773,568 |
| 1,000 typical saves | 2,334,810 | 3,100,672 | 3,440,640 |
| 1,000 richer saves | 4,126,810 | 5,156,864 | 5,701,632 |
| 1,000 saves with varied vocabulary | 4,126,810 | 5,156,864 | 7,749,632 |

Incremental indexing grows the last case to 7,761,920 used bytes. A 100-item edit batch is rejected by the 8 MB used-page check in the varied-vocabulary case; re-inserting 100 saves after deleting them is also rejected. Source data and usage remain at their previous committed values. A logical allowance does not guarantee that all text can be indexed or that later edits will fit.

With 20,000-byte notes, 200 saves use approximately 4.72 MB of logical data; the next 100-item batch exceeds the 5 MB allowance and rolls back. A separate fixture fills the local app's 20,000-code-point note limit with emoji, using 80,000 UTF-8 bytes per note: 50 saves fit and the next ten-save batch rolls back. Multibyte bytes are counted rather than JavaScript string length. Count limits and concurrency at the final available item are tested separately.

### Used pages are not allocated physical storage

The prototype's size measurement is `sql.databaseSize`. In the pinned workerd implementation it is `(page_count - freelist_count) * page_size`, excluding allocated free pages. The runtime denies direct `PRAGMA page_count` access. A separate local persisted-database inspection is therefore required to compare used pages with allocated pages and database/WAL files. See the [pinned workerd implementation](https://github.com/cloudflare/workerd/blob/v1.20261104.1/src/workerd/api/sql.c%2B%2B) and [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).

Independent reproduction with 1,000 varied saves and a 100-save deletion found 7,360,512 used bytes but 8,196,096 allocated page bytes. Database and WAL file sizes are another measurement and must not be added blindly to the page count as if they were separate user data. Local file allocation is not a measurement of Cloudflare's billable storage, replication or recovery overhead.

The committed allocation probe reproduces that difference. Without FTS, its 1,000-save database allocates 5,148,672 bytes, unchanged after deleting 100 saves and performing 4,500 subsequent edits. With FTS, a rejected write preserves source data and allocated pages but grows the local WAL from 4,795,712 to 5,014,072 bytes. The probe omits the separate operational seed used in the main table, explaining the small baseline difference. Neither result is a universal allocation bound.

Rolling back FTS schema creation on a populated database produces an internal error in the pinned workerd version. A regression test expects that failure, restarts the object and verifies unchanged exports/accounting and absent FTS schema. Ordinary index-migration rollback and deletion rollback also pass. FTS installation is not a supported production migration strategy in this checkpoint.

**The planned 8,000,000-byte physical budget is not yet enforced or proven.** The experiment enforces a used-page threshold and demonstrates transactional source/usage rollback. Renaming that metric does not satisfy the physical-budget requirement. Cloud storage accounting must be reconciled with the provider's meter, or a supported alternative storage/compaction bound must be adopted before P1 closes.

### Resource counters have limits

The cursor counters report 700 row writes per 100-save batch without FTS, 800 with incremental FTS, 800 for 100 indexed edits, and 400 for 100 indexed deletions (300 without FTS). Adding the status index to 1,000 records reports 1,002 writes. Failed batches still consume completed SQL work; the experiment does not refund it.

A full FTS rebuild reports only six writes while growing the varied database by 2,592,768 bytes. These counters cannot certify the full account charge for hidden FTS work. Platform documentation says index and FTS work must be counted; compare the local counters with actual account metrics before accepting a daily ingestion budget. [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

The 25-result list probe reads 25 rows through a covering index containing only IDs and dates. P2 metadata previews and additional filters will have different costs. Ranked search can read more rows than it returns. Local elapsed request times include HTTP/tooling overhead; they are not Worker CPU, active object duration, network latency guarantees or deployed authentication performance.

## Decisions for the next contract

These are proposed P2 constraints, not implemented hosted enforcement:

1. Start with bounded title/tag/metadata search and no full-text index. Keep source bodies and notes separate and load bodies on demand. Full-text indexing needs independent size, mutation and accounting gates before it can be enabled.
2. Reserve maintenance space: use 7,000,000 used bytes as a provisional normal-write threshold inside the planned 8,000,000-byte workspace budget. This margin mitigates growth; it does not resolve the allocated-page accounting gap.
3. Bound each mutation request by both 25 records and 256 KiB of UTF-8 payload. Preserve the 1,000-save and 5,000,000-logical-byte planning limits, with explicit rejection rather than truncation.
4. Initially reserve `16 * mutation_count + 32` write units per batch, with a minimum of 32. A 25-record grant is 432 units against 175 writes if scaled proportionally from the measured 700-write, 100-record no-FTS insert. The final P2 schema, registry, retries and operational bookkeeping must fit the reservation in measured tests. Failed attempts retain their grant; local cursor differences do not automatically refund it.
5. Provisionally divide the 100,000 daily write allowance into 40,000 new-ingestion units, 30,000 interactive/deletion units, 20,000 accepted-job completion/reconciliation units and 10,000 unallocated guard units. Cap new ingestion at 2,000 mutations/day across the whole beta as well as the unit budget. Eighty full 25-record grants reserve 34,560 units; smaller or rejected batches can admit fewer saves.

This is a conservative admission proposal, not a demonstrated upper bound on billing. Requests, reads, object duration, storage and ordinary Worker CPU have independent limits. Holding 500 workspaces is a different claim from accepting 500 full imports in a day. All of these limits need the final contract and cloud measurements before real admission.

The quota split uses the documented Free allowance of 100,000 SQL rows written per day; other account workloads share it. [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)

## Remaining gates

- Measure synthetic RS256 verification on the ordinary Worker against its Free CPU allowance; measure cold/warm object work and idle behavior separately. Local wall-clock timing does not establish either. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
